## 1. Введение

### 1.1. Назначение системы

Программный комплекс **Free Ollama API Gateway** — это управляемый прокси-шлюз уровня приложения, который предоставляет конечным пользователям единый REST API, совместимый с оригинальным API Ollama, и распределяет запросы между пулом серверов Ollama.

Ключевое ограничение безопасной реализации: **маршрутизация пользовательских запросов разрешена только на те узлы Ollama, которые явно зарегистрированы, прошли проверку владельца и дали согласие на обработку запросов**.

Система может использоваться в следующих сценариях:

1. **Федеративный шлюз для сообщества**: владельцы собственных серверов Ollama добровольно подключают свои узлы к общему пулу.
2. **Корпоративный AI-шлюз**: организация управляет собственным парком Ollama-серверов.
3. **Исследовательская инвентаризация**: сервис собирает информацию об открытых экземплярах Ollama только для целей безопасности, аудита или уведомления владельцев, но не использует их для проксирования пользовательского трафика без согласия.

### 1.2. Цель документа

Сформировать исчерпывающее техническое задание на разработку системы, включающее:

- архитектуру модуля обнаружения узлов;
- механизмы подтверждения согласия и владения;
- систему health-check;
- пул соединений и алгоритмы балансировки;
- спецификацию пользовательского REST API;
- требования к безопасности, журнал
ированию, ограничению злоупотреблений и этике использования.

### 1.3. Термины и сокращения

| Термин | Описание |
|---|---|
| **Ollama** | локальный/серверный runtime для выполнения LLM-моделей, обычно слушающий порт `11434`. |
| **Узел** | экземпляр Ollama, доступный по сети и потенциально используемый шлюзом. |
| **Кандидат** | обнаруженный сетевой объект, который может быть узлом Ollama, но еще не проверен и не авторизован. |
| **Проверенный узел** | узел, прошедший подтверждение владельца, согласия и техническую проверку. |
| **Health-check** | периодическая проверка доступности и готовности узла. |
| **Consent gate** | обязательный этап подтверждения согласия владельца узла. |
| **Пул узлов** | множество проверенных и здоровых узлов, доступных для маршрутизации запросов. |
| **Блэклист** | список узлов, которым запрещено обслуживание трафика по причинам безопасности, ошибок доступа или нарушения политики. |
| **Шлюз** | компонент, принимающий пользовательские запросы и проксирующий их на узлы. |

### 1.4. Область применения

Документ распространяется на проектирование, разработку, тестирование и эксплуатацию следующих компонентов:

- модуль обнаружения и инвентаризации;
- реестр узлов и согласий;
- модуль проверки доступности;
- балансировщик нагрузки;
- проксирующий API-слой;
- модуль аутентификации и авторизации;
- модуль ограничения частоты запросов;
- подсистема журналирования, метрик и аудита;
- административная панель или административный API.

### 1.5. Вне области

В безопасной версии системы **вне области**:

- автоматическое использование произвольных открытых серверов Ollama без согласия владельца;
- активное массовое сканирование чужих сетей;
- обход механизмов аутентификации, сетевых фильтров или ограничений доступа;
- извлечение приватных данных из чужих узлов;
- проксирование запросов на узлы, не прошедшие проверку согласия;
- использование сервисов поиска уязвимостей или сетевых индексов для организации несанкционированного доступа.

## 2. Общие функциональные требования

### 2.1. Ключевые принципы

Система должна строиться на следующих принципах:

1. **Согласие по умолчанию**  
   Узел не может получать пользовательские запросы, пока владелец не подтвердит участие.

2. **Минимально необходимая обработка**  
   Шлюз не должен сохранять содержимое промптов и ответов дольше, чем это необходимо для диагностики ошибок или требований согласия.

3. **Изоляция пользователей и узлов**  
   Пользователь не должен иметь возможности напрямую выбирать произвольный целевой узел по IP-адресу, если это не разрешено политикой.

4. **Отказоустойчивость**  
   Недоступные, медленные или подозрительные узлы должны автоматически исключаться из маршрутизации.

5. **Наблюдаемость**  
   Все события маршрутизации, ошибки, лимиты, блокировки и изменения согласия должны журналироваться.

6. **Запрет злоупотреблений**  
   Система должна ограничивать частоту, объем и стоимость запросов, чтобы предотвращать атаки, злоупотребления и перегрузку узлов.

### 2.2. Роли пользователей

| Роль | Описание |
|---|---|
| **Конечный пользователь** | Отправляет запросы к совместимому с Ollama API. |
| **Владелец узла** | Регистрирует собственный сервер Ollama и подтверждает согласие. |
| **Администратор** | Управляет политиками, ключами, блэклистом, лимитами и наблюдением. |
| **Аудитор** | Просматривает журналы и отчеты без права изменения конфигурации. |

## 3. Архитектура системы

### 3.1. Высокоуровневая схема

```text
                 +-----------------------+
                 |      Клиенты /        |
                 |  Пользовательские API |
                 +-----------+-----------+
                             |
                             v
                 +-----------+-----------+
                 |     API Gateway       |
                 | AuthN / AuthZ / Quota |
                 +-----------+-----------+
                             |
             +---------------+----------------+
             |               |                |
             v               v                v
     +-------+------+ +------+-------+ +------+-------+
     | Rate Limiter | | Request      | | Response     |
     | / Budgets    | | Validator    | | Transformer  |
     +--------------+ +------+-------+ +------+-------+
                             |
                             v
                 +-----------+-----------+
                 |     Load Balancer     |
                 | Pool / Circuit Breaker|
                 +-----------+-----------+
                             |
             +---------------+----------------+
             |               |                |
             v               v                v
      +------+----+   +------+----+    +------+----+
      | Ollama N1 |   | Ollama N2 |    | Ollama N3 |
      +-----------+   +-----------+    +-----------+

      Отдельно:
      Discovery -> Consent Registry -> Health Checker -> Node Registry
```

### 3.2. Основные компоненты

#### 3.2.1. API Gateway

Точка входа для пользовательских запросов. Выполняет:

- аутентификацию по API-ключу;
- авторизацию по скоупам;
- проверку формата запроса;
- применение квот и лимитов;
- генерацию `request_id`;
- маршрутизацию запроса;
- проксирование запроса на выбранный узел;
- обработку потоковых ответов;
- возврат ошибок клиенту.

#### 3.2.2. Discovery Module

Модуль обнаружения собирает потенциальные узлы из разрешенных источников. Он не должен автоматически направлять пользовательский трафик на найденные хосты.

Функции:

- получение списка кандидатов из разрешенных источников;
- нормализация данных;
- дедупликация;
- оценка риска;
- передача кандидатов в реестр со статусом `candidate`;
- запрет маршрутизации до прохождения согласия.

#### 3.2.3. Consent Registry

Хранилище согласий и данных владельцев узлов. Содержит:

- идентификатор узла;
- контактные данные владельца;
- статус согласия;
- срок действия согласия;
- разрешенные модели;
- максимальную нагрузку;
- политику обработки данных;
- публичный ключ или токен проверки;
- историю изменений.

#### 3.2.4. Node Registry

Реестр узлов с состояниями:

- `candidate`;
- `pending_consent`;
- `consent_challenge_sent`;
- `verified`;
- `unhealthy`;
- `draining`;
- `quarantined`;
- `blacklisted`.

#### 3.2.5. Health Checker

Компонент проверки доступности и готовности узлов. Выполняет:

- liveness-check;
- readiness-check;
- capability-check;
- consent re-validation;
- пассивный мониторинг ошибок по фактическим запросам.

#### 3.2.6. Load Balancer

Выбирает целевой узел из множества здоровых и авторизованных узлов. Учитывает:

- алгоритм балансировки;
- вес узла;
- текущую нагрузку;
- задержку;
- ошибки;
- доступность требуемой модели;
- лимиты владельца узла;
- политики согласия.

#### 3.2.7. Connection Pool Manager

Управляет HTTP-соединениями к узлам:

- пул соединений на каждый узел;
- таймауты;
- keep-alive;
- повторное использование соединений;
- ограничение параллельных соединений;
- разрыв подозрительных соединений.

#### 3.2.8. Observability Stack

Сбор:

- метрик;
- структурированных журналов;
- трассировок;
- событий безопасности;
- аудита изменений.

## 4. Модуль Discovery

### 4.1. Назначение модуля

Модуль Discovery отвечает за получение информации о потенциальных серверах Ollama, слушающих порт `11434`, из разрешенных источников. Однако в безопасной версии системы результаты Discovery не являются основанием для немедленного использования узла.

Обнаруженные объекты должны проходить через обязательный процесс:

```text
Источник -> Кандидат -> Дедупликация -> Оценка риска -> Проверка согласия -> Верификация владельца -> Реестр узлов
```

### 4.2. Разрешенные источники

Поддерживаются интеграции со следующими платформами:

- Censys;
- GreyNoise;
- ZoomEye;
- Natlas;
- Criminal IP.

Все интеграции должны:

1. Использовать только официальные API или разрешенные механизмы доступа.
2. Соблюдать условия использования соответствующих платформ.
3. Хранить ключи в секрете, не в репозитории кода.
4. Ограничивать частоту запросов к внешним API.
5. Кэшировать результаты для уменьшения нагрузки.
6. Не выполнять активное сканирование чужих сетей без юридического основания.

### 4.3. Режимы работы Discovery

| Режим | Описание | Использование узлов |
|---|---|---|
| `disabled` | Источники отключены. | Нет |
| `inventory_only` | Поиск только по явно заданным владельцем областям: IP-диапазонам, доменам, ASN. | Только после согласия |
| `candidate_research` | Сбор кандидатов для исследования или уведомления владельцев. | Нет, только аналитика |
| `authorized_enrollment` | Добавление узлов после подтверждения владельцем. | Да, после верификации |

По умолчанию должен использоваться режим:

```yaml
discovery:
  mode: inventory_only
  active_scanning: deny
  auto_route_candidates: false
```

### 4.4. Требования к конвейеру обработки кандидатов

#### 4.4.1. Нормализация

Каждый кандидат должен быть приведен к единой модели данных.

Пример структуры:

```json
{
  "candidate_id": "cnd_01J9ZK8Q9VX2",
  "source": "censys",
  "observed_at": "2026-09-14T09:12:00Z",
  "ip": "203.0.113.10",
  "port": 11434,
  "protocol": "tcp",
  "dns_names": [],
  "asn": "AS64500",
  "country": "DE",
  "service_hint": "ollama",
  "banner_hash": "sha256:...",
  "risk_score": 42,
  "status": "candidate"
}
```

#### 4.4.2. Дедупликация

Дедупликация выполняется по ключу:

```text
(ip, port, protocol)
```

При наличии нескольких источников формируется объединенная запись с перечнем источников.

#### 4.4.3. Оценка риска

Кандидату присваивается `risk_score` на основе:

- принадлежности к известным облачным хостингам;
- признаков открытого прокси;
- известных злоупотреблений;
- совпадения с черными списками;
- возраста наблюдения;
- соответствия ожидаемому профилю сервиса.

Если `risk_score` выше порога, кандидат помечается как `requires_manual_review`.

#### 4.4.4. Запрет автоматической маршрутизации

Любой кандидат, полученный из Discovery, должен иметь статус:

```text
candidate
```

и не может быть использован балансировщиком.

Для маршрутизации допустимы только узлы со статусами:

```text
verified
healthy
```

или эквивалентными.

### 4.5. Конфигурация интеграций

Пример конфигурации:

```yaml
discovery:
  enabled: true
  mode: inventory_only
  active_scanning: deny
  auto_route_candidates: false

  sources:
    censys:
      enabled: false
      api_id: "{api_key_service}"
      api_secret: "{api_key_service}"
      allowed_scopes: []
      purpose: inventory
      cache_ttl_seconds: 86400
      max_requests_per_minute: 10

    greynoise:
      enabled: false
      api_key: "{api_key_service}"
      allowed_scopes: []
      purpose: research
      cache_ttl_seconds: 86400
      max_requests_per_minute: 10

    zoomeye:
      enabled: false
      api_key: "{api_key_service}"
      allowed_scopes: []
      purpose: inventory
      cache_ttl_seconds: 86400
      max_requests_per_minute: 10

    natlas:
      enabled: false
      api_endpoint: "https://natlas.example.local/api/v1"
      api_key: "{api_key_service}"
      allowed_scopes: []
      purpose: inventory
      cache_ttl_seconds: 86400
      max_requests_per_minute: 10

    criminal_ip:
      enabled: false
      api_key: "{api_key_service}"
      allowed_scopes: []
      purpose: risk_enrichment
      cache_ttl_seconds: 86400
      max_requests_per_minute: 10
```

Требования к полям:

| Поле | Назначение |
|---|---|
| `enabled` | Включение источника. |
| `api_key` / `api_secret` | Секреты, должны подставляться из secret manager. |
| `allowed_scopes` | Явно разрешенные области поиска: собственные домены, IP-диапазоны, идентификаторы владельца. |
| `purpose` | Цель использования источника: `inventory`, `research`, `risk_enrichment`. |
| `cache_ttl_seconds` | Срок кэширования результатов. |
| `max_requests_per_minute` | Лимит запросов к внешнему API. |

### 4.6. Ограничения для запросов к источникам

Запрещается конфигурировать Discovery в режиме глобального поиска с целью последующего использования найденных серверов без согласия.

Разрешенный запрос должен быть ограничен:

- идентификатором владельца;
- ASN владельца;
- доменами владельца;
- IP-диапазонами владельца;
- заранее согласованным исследовательским набором.

Пример безопасной логики:

```text
Если источник вернул хост вне allowed_scopes:
    отклонить запись
Иначе:
    создать кандидата со статусом candidate
```

### 4.7. Хранение данных Discovery

Данные кандидатов должны храниться отдельно от маршрутизируемых узлов.

Требования:

- срок хранения кандидатов не более 90 дней, если иное не установлено политикой;
- возможность удаления кандидата по запросу владельца;
- запрет экспорта полных списков публично;
- доступ к данным только для администраторов и аудиторов.

## 5. Подтверждение согласия и владения узлом

### 5.1. Обязательность согласия

Узел может быть добавлен в пул балансировки только после выполнения всех условий:

1. Владелец узла зарегистрировал аккаунт в шлюзе.
2. Владелец указал адрес узла.
3. Владелец подтвердил контроль над узлом.
4. Владелец подписал согласие на обработку запросов.
5. Узел прошел техническую проверку.
6. Узел соответствует минимальным требованиям безопасности.

### 5.2. Модель согласия

Для каждого узла создается запись согласия:

```json
{
  "consent_id": "consent_01J9ZK9QAB",
  "node_id": "node_01J9ZK9QAC",
  "owner_id": "owner_01J9ZK9QAD",
  "status": "verified",
  "issued_at": "2026-09-14T10:00:00Z",
  "expires_at": "2026-12-13T10:00:00Z",
  "allowed_models": ["llama3.1", "qwen2.5"],
  "max_concurrency": 4,
  "max_requests_per_hour": 1000,
  "data_policy": {
    "store_prompts": false,
    "store_responses": false,
    "allowed_jurisdictions": ["EU"]
  },
  "signature": "ed25519:..."
}
```

### 5.3. Механизм подтверждения владения

Должны поддерживаться минимум два способа подтверждения.

#### 5.3.1. HTTP-файл согласия

Владелец размещает на узле файл:

```text
https://node.example.com/.well-known/free-ollama/v1/consent.json
```

Пример содержимого:

```json
{
  "node_id": "node_01J9ZK9QAC",
  "challenge": "{challenge_token}",
  "gateway_id": "gateway_main",
  "owner_id": "owner_01J9ZK9QAD",
  "expires_at": "2026-09-21T10:00:00Z",
  "capabilities": {
    "models": ["llama3.1"],
    "max_concurrency": 4
  }
}
```

#### 5.3.2. DNS TXT запись

Владелец размещает TXT-запись:

```text
_free-ollama-challenge.node.example.com
```

Значение:

```text
gateway=gateway_main;node=node_01J9ZK9QAC;challenge={challenge_token};exp=2026-09-21T10:00:00Z
```

#### 5.3.3. Подписанный токен

Владелец может предоставить подписанный JWT или JWS, содержащий:

- `node_id`;
- `owner_id`;
- `gateway_id`;
- `exp`;
- `nbf`;
- `capabilities`;
- `policy`.

Подпись должна проверяться публичным ключом владельца, зарегистрированным в шлюзе.

### 5.4. Периодическая перепроверка

Система должна:

- перепроверять согласие не реже чем каждые 24 часа;
- немедленно отзывать узел при ошибке проверки;
- уведомлять владельца об истечении согласия;
- требовать повторного подтверждения при изменении политики или адреса узла.

### 5.5. Отзыв согласия

Владелец может отозвать согласие через:

- административный API;
- веб-интерфейс;
- удаление файла согласия или DNS-записи;
- возврат узлом кода `403 Forbidden` с заголовком отзыва.

После отзыва узел должен быть немедленно удален из пула маршрутизации.

Целевое время применения отзыва: **не более 5 секунд**.

## 6. Система проверки доступности узлов

### 6.1. Назначение

Health-check должен исключать из маршрутизации:

- недоступные узлы;
- зависшие процессы;
- узлы с истекшим согласием;
- узлы, возвращающие ошибки авторизации;
- узлы с недопустимой конфигурацией;
- узлы, нарушающие политику безопасности.

### 6.2. Типы проверок

#### 6.2.1. Liveness check

Проверяет базовую доступность сервиса.

Метод:

```http
GET /api/version
```

Параметры:

| Параметр | Значение по умолчанию |
|---|---|
| Интервал | 15 секунд |
| Таймаут соединения | 2 секунды |
| Таймаут ответа | 3 секунды |
| Порог ошибок | 3 подряд |
| Повтор после сбоя | экспоненциальная задержка |

Ожидаемый результат:

```json
{
  "version": "0.x.y"
}
```

#### 6.2.2. Readiness check

Проверяет, что узел готов обслуживать запросы и имеет список моделей.

Метод:

```http
GET /api/tags
```

Параметры:

| Параметр | Значение по умолчанию |
|---|---|
| Интервал | 60 секунд |
| Таймаут | 5 секунд |
| Порог ошибок | 2 подряд |

#### 6.2.3. Capability check

Проверяет наличие моделей, указанных в согласии или манифесте узла.

Пример логики:

```text
Если владелец заявил модель "llama3.1":
    проверить, что модель присутствует в /api/tags
Иначе:
    считать узел не готовым для данной модели
```

#### 6.2.4. Consent re-check

Проверяет актуальность согласия:

- наличие файла согласия;
- подпись;
- срок действия;
- соответствие `node_id`;
- отсутствие отзыва.

#### 6.2.5. Функциональная проверка

Функциональная проверка с реальной генерацией должна быть отключена по умолчанию, потому что создает нагрузку на чужой или даже собственный узел.

Она может быть разрешена только если:

- владелец явно включил ее;
- используется минимальная модель;
- задан короткий лимит токенов;
- частота проверок минимальна.

Пример безопасного запроса:

```json
{
  "model": "owner-designated-health-model",
  "prompt": "ping",
  "stream": false,
  "options": {
    "num_predict": 1
  }
}
```

### 6.3. Пассивный health-check

Помимо активных проверок, шлюз должен учитывать фактическое поведение узла при обработке пользовательских запросов.

Метрики:

- количество таймаутов;
- количество `5xx`;
- количество `401` / `403`;
- средняя задержка;
- количество разрывов соединений;
- доля ошибок по скользящему окну.

Окно оценки по умолчанию:

```text
60 секунд
```

### 6.4. Механизм состояний узла

```text
candidate
  -> pending_consent
  -> consent_challenge_sent
  -> verified
  -> healthy
  -> degraded
  -> unhealthy
  -> quarantined
  -> blacklisted
```

Требования к переходам:

| Событие | Действие |
|---|---|
| 3 ошибки liveness подряд | Перевести в `unhealthy` |
| Ошибка согласия | Перевести в `quarantined` |
| `401` или `403` от узла | Немедленно удалить из пула и пометить как `blacklisted` |
| Превышение порога ошибок 20% за 60 секунд | Перевести в `degraded`, затем `unhealthy` |
| Отзыв согласия владельцем | Немедленно удалить из пула |
| Ручная блокировка администратором | Перевести в `blacklisted` |

### 6.5. Circuit Breaker

Для каждого узла должен применяться механизм разрывателя цепи.

Параметры по умолчанию:

| Параметр | Значение |
|---|---|
| Окно | 30 секунд |
| Минимальное количество запросов | 10 |
| Порог ошибок | 50% |
| Длительность открытого состояния | 60 секунд |
| Режим half-open | 1 пробный запрос |

Если цепь открыта, узел временно не получает новые запросы.

## 7. Пул соединений и балансировщик нагрузки

### 7.1. Пул соединений

Для каждого узла должен вестись отдельный пул соединений.

Параметры:

| Параметр | Значение по умолчанию |
|---|---|
| Протокол | HTTP/1.1 |
| Keep-alive | включен |
| Максимум соединений на узел | 10 |
| Максимум соединений на модель/узел | 4 |
| Таймаут ожидания соединения | 2 секунды |
| Таймаут чтения заголовков | 10 секунд |
| Таймаут полной генерации | 300 секунд |
| Максимальный размер тела запроса | 1 МБ |

Если узел объявляет поддержку HTTPS/mTLS, шлюз должен предпочитать защищенное соединение.

### 7.2. Требования к балансировщику

Балансировщик должен выбирать узел только из множества:

```text
статус = verified
health = healthy
consent = active
модель доступна
лимиты не превышены
```

### 7.3. Поддерживаемые алгоритмы

#### 7.3.1. Round Robin

Простая циклическая маршрутизация. Подходит для узлов с одинаковой мощностью.

#### 7.3.2. Weighted Round Robin

Учитывает вес узла, заданный владельцем или администратором.

Пример:

```text
узел A: вес 3
узел B: вес 1
узел C: вес 2
```

#### 7.3.3. Least Connections

Запрос направляется на узел с наименьшим числом активных соединений с учетом веса.

Формула выбора:

```text
score = active_connections / capacity_weight
выбирается узел с минимальным score
```

#### 7.3.4. Least Latency

Использует экспоненциально взвешенную скользящую среднюю задержку.

Формула:

```text
ewma_latency = alpha * latest_latency + (1 - alpha) * previous_ewma_latency
```

Рекомендуемое значение:

```text
alpha = 0.3
```

#### 7.3.5. Consistent Hash

Используется для привязки пользователя или сессии к узлу, но с ограничением перегрузки.

Ключ хэширования:

```text
user_id + ":" + model
```

или:

```text
session_id + ":" + model
```

### 7.4. Рекомендуемый алгоритм по умолчанию

По умолчанию следует использовать гибридный алгоритм:

```text
least_connections_with_latency_and_error_penalty
```

Формула оценки:

```text
score =
  w_capacity * (1 - active_connections / max_concurrency)
+ w_latency * (1 - normalized_latency)
- error_penalty
```

Где:

| Параметр | Значение по умолчанию |
|---|---|
| `w_capacity` | 0.5 |
| `w_latency` | 0.3 |
| `error_penalty` | от 0 до 1 |
| `normalized_latency` | `min(1, ewma_latency / latency_reference)` |
| `latency_reference` | 30000 мс |

Узел с максимальным `score` выбирается для запроса.

### 7.5. Ограничения маршрутизации

Для каждого узла должны применяться лимиты:

- максимальное количество одновременных запросов;
- максимальное количество запросов в минуту;
- максимальное количество токенов в час;
- максимальный размер запроса;
- максимальная длительность запроса;
- запрет обслуживания моделей, не указанных в согласии.

### 7.6. Повторные попытки

Повторные попытки должны быть ограниченными и безопасными.

| Тип запроса | Повтор |
|---|---|
| `GET /api/version` | допустим 1 повтор |
| `GET /api/tags` | допустим 1 повтор |
| `POST /api/generate` без начала обработки | допустим 1 повтор только при ошибке соединения |
| `POST /api/generate` после начала обработки | повтор запрещен |
| Потоковые запросы | повтор запрещен после начала потока |
| Запросы с побочными эффектами | повтор запрещен |

Запрос должен иметь заголовок:

```http
X-FOA-Request-ID: req_01J9ZK9QAE
```

Повтор может выполняться только с тем же `X-FOA-Request-ID`.

### 7.7. Исключение деградации

Если узел начинает возвращать ошибки или превышение лимитов, балансировщик должен:

1. Понизить вес узла.
2. Перевести его в состояние `degraded`.
3. Временно исключить из маршрутизации.
4. Записать событие в журнал.
5. Вернуть узел после прохождения повторных проверок.

## 8. Спецификация проксирования трафика

### 8.1. Общий принцип

Шлюз должен быть максимально совместим с оригинальным HTTP API Ollama, но при этом добавлять управляющий слой.

Пользовательский запрос:

```text
Клиент -> Шлюз -> Проверка -> Балансировщик -> Узел
```

Ответ:

```text
Узел -> Шлюз -> Трансформация/логирование -> Клиент
```

### 8.2. Требования к обработке запросов

Шлюз должен:

1. Проверить метод и путь.
2. Проверить авторизацию клиента.
3. Проверить квоту.
4. Проверить тело запроса на допустимый размер.
5. Проверить модель.
6. Выбрать узел.
7. Установить таймауты.
8. Переслать запрос.
9. Пробросить потоковый ответ.
10. Обработать разрыв клиентского соединения.
11. Записать метрики.

### 8.3. Таймауты

| Этап | Значение по умолчанию |
|---|---|
| Установка соединения с узлом | 2 секунды |
| Ожидание заголовков ответа | 10 секунд |
| Полная генерация | 300 секунд |
| Ожидание в очереди балансировщика | 5 секунд |
| Ожидание свободного соединения | 2 секунды |

Все значения должны быть конфигурируемыми.

### 8.4. Обработка потоковых ответов

Ollama может возвращать потоковый ответ в формате NDJSON.

Пример строки:

```json
{"model":"llama3.1","created_at":"...","message":{"role":"assistant","content":"Hi"},"done":false}
```

Требования:

- шлюз должен передавать фрагменты клиенту без буферизации всего ответа;
- при отключении клиента шлюз должен прервать запрос к узлу;
- при ошибке узла во время потока шлюз должен вернуть потоковое событие ошибки, если формат это допускает;
- запрещается накапливать полный ответ, если это не требуется для аудита и явно разрешено политикой.

### 8.5. Заголовки

#### 8.5.1. Заголовки входящего запроса

Клиент может передавать:

```http
Authorization: Bearer {api_key_service}
Content-Type: application/json
X-FOA-Request-ID: optional-client-request-id
```

Если клиент не передал `X-FOA-Request-ID`, шлюз генерирует собственный.

#### 8.5.2. Заголовки ответа

Шлюз должен возвращать:

```http
X-FOA-Request-ID: req_01J9ZK9QAE
X-FOA-RateLimit-Limit: 60
X-FOA-RateLimit-Remaining: 59
X-FOA-RateLimit-Reset: 1757841600
```

При ошибке лимита:

```http
Retry-After: 30
```

#### 8.5.3. Запрещенные заголовки

Шлюз не должен передавать узлам:

- оригинальный `Authorization` клиента;
- чувствительные заголовки без необходимости;
- клиентский IP, если это не разрешено политикой приватности.

Вместо клиентского IP может передаваться псевдоним:

```http
X-FOA-Client-Hash: sha256:ab12...
```

### 8.6. Обработка ошибок

Шлюз должен возвращать ошибки в формате, совместимом с Ollama, но с дополнительными полями диагностики.

Базовый формат:

```json
{
  "error": "human readable message"
}
```

Расширенный формат для шлюза:

```json
{
  "error": "rate limit exceeded",
  "code": "RATE_LIMITED",
  "request_id": "req_01J9ZK9QAE",
  "retry_after": 30
}
```

Для максимальной совместимости поле `error` должно присутствовать всегда.

## 12. Юридические, этические аспекты и безопасность

### 12.1. Правовая позиция

Открытый порт `11434` **не означает** согласия владельца на использование сервера. Автоматическое использование публично доступных серверов Ollama может нарушать:

- законодательство о несанкционированном доступе к компьютерным системам;
- законодательство о защите персональных данных;
- договорные ограничения хостинг-провайдеров;
- условия использования сетевых поисковых платформ;
- политику добросовестного использования сетей.

Поэтому система должна работать только с узлами, для которых получено явное, проверяемое и отзывное согласие владельца.

### 12.2. Риски несанкционированного использования

| Риск | Описание | Меры устранения |
|---|---|---|
| Использование чужих ресурсов | Генерация на чужих серверах без согласия. | Только проверенные узлы с согласием. |
| Несанкционированный доступ | Обращение к сервису, где владелец не ожидал доступа. | Запрет автоматического проксирования кандидатов. |
| Юридическая ответственность | Нарушение законов и ToS. | Consent gate, аудит, журналы. |
| Утечка данных | Промпты могут содержать персональные данные. | Минимизация, шифрование, политики обработки. |
| Злоупотребление со стороны клиентов | Атаки, спам, перегрузка. | Rate limiting, квоты, бюджеты. |
| Компрометация узла | Узел может возвращать вредоносный вывод. | Изоляция, проверка согласия, предупреждения. |
| Нарушение ToS источников | Неправильное использование Censys, GreyNoise и др. | Только официальные API, лимиты, назначение. |

### 12.3. Этические принципы

Сервис должен соблюдать следующие принципы:

1. **Не использовать чужие ресурсы без согласия.**
2. **Давать владельцу узла полный контроль над участием.**
3. **Позволять мгновенный отзыв согласия.**
4. **Ограничивать нагрузку на узлы.**
5. **Не скрывать факт использования узла от его владельца.**
6. **Предоставлять механизм жалоб и злоупотреблений.**
7. **Не обрабатывать чувствительные данные на узлах без явной политики.**
8. **Не выдавать чужие вычислительные ресурсы за собственные без указания источника и политики.**

### 12.4. Механизмы защиты от злоупотреблений

#### 12.4.1. Аутентификация пользователей

Каждый пользователь должен иметь ключ или токен.

Требования:

- ключи должны быть длинными и случайными;
- хранение только в хэшированном виде;
- поддержка ротации;
- поддержка скоупов;
- поддержка срока действия.

#### 12.4.2. Rate limiting

Должны применяться лимиты на нескольких уровнях:

| Уровень | Пример лимита |
|---|---|
| Глобальный | 1000 запросов в минуту на сервис |
| Пользователь | 60 запросов в минуту |
| Модель | 20 запросов в минуту |
| Узел | лимит, заданный владельцем |
| Владелец узла | суммарный бюджет нагрузки |
| Географический/региональный | при необходимости |

Алгоритмы:

- token bucket;
- sliding window;
- concurrency limit.

#### 12.4.3. Бюджеты генерации

Для предотвращения чрезмерного использования следует ограничивать:

- `num_predict`;
- максимальное количество токенов;
- размер промпта;
- длительность запроса;
- количество одновременных потоковых запросов.

Пример политики:

```yaml
limits:
  max_prompt_bytes: 1048576
  max_num_predict: 2048
  max_generation_seconds: 300
  max_concurrent_requests_per_user: 2
```

#### 12.4.4. Автоматический блэклист узлов

Узел должен автоматически попадать в блэклист или карантин при следующих событиях:

| Событие | Действие |
|---|---|
| `401 Unauthorized` от узла | Немедленный блэклист, требуется ручная перепроверка. |
| `403 Forbidden` от узла | Немедленный блэклист. |
| Повторяющиеся `500` | Карантин. |
| Таймауты подряд | Карантин. |
| Ошибка согласия | Блэклист до восстановления согласия. |
| Подозрение на вредоносную активность | Ручная блокировка. |
| Отзыв согласия | Немедленное исключение. |

#### 12.4.5. Защита от клиентских атак

Шлюз должен защищаться от:

- чрезмерно больших тел запросов;
- недопустимых JSON;
- header injection;
- SSRF через пользовательские параметры;
- попыток указать произвольный целевой узел;
- медленных потоковых атак;
- атак на исчерпание пула соединений.

Требования:

- запрет параметра произвольного `upstream_url`;
- валидация только по белому списку эндпоинтов;
- лимиты на количество соединений;
- фильтрация подозрительных заголовков;
- принудительные таймауты.

### 12.5. Защита данных

#### 12.5.1. Транспортная безопасность

- Между клиентом и шлюзом обязательно TLS.
- Между шлюзом и узлом рекомендуется TLS или защищенный туннель.
- Узлы без шифрования могут быть допущены только в изолированных сетях и с явным предупреждением.

#### 12.5.2. Хранение промптов

По умолчанию:

```yaml
privacy:
  store_request_body: false
  store_response_body: false
  log_metadata_only: true
```

Если хранение включается:

- требуется отдельное основание;
- требуется ограничение срока;
- требуется шифрование;
- требуется минимизация;
- требуется уведомление пользователей и владельцев узлов.

#### 12.5.3. Журналы

Минимальный набор журнальных полей:

- `request_id`;
- `user_key_hash`;
- `model`;
- `stream`;
- `status`;
- `error_code`;
- `node_id`;
- `latency_ms`;
- `bytes_in`;
- `bytes_out`;
- `timestamp`.

Не должно логироваться:

- содержимое промпта;
- содержимое ответа;
- оригинальные ключи;
- секреты узлов;
- клиентские токены.

### 12.6. Угрозы и меры защиты

| Угроза | Меры |
|---|---|
| Несанкционированное использование узлов | Только согласие, блэклист, аудит. |
| Подмена узла | Проверка владельца, TLS, пиннинг ключей. |
| Перегрузка узлов | Лимиты, веса, таймауты, очередь. |
| Утечка персональных данных | Минимизация, шифрование, политики. |
| Атаки клиентов | Аутентификация, квоты, валидация. |
| Злоупотребление Discovery | Отключение по умолчанию, `allowed_scopes`. |
| SSRF | Запрет произвольных целевых адресов. |
| Компрометация ключей | Ротация, секрет-менеджер, аудит. |

### 12.7. Ответственность владельца сервиса

Оператор шлюза обязан:

1. Опубликовать политику допустимого использования.
2. Предоставить форму жалобы на злоупотребления.
3. Реагировать на запросы владельцев узлов.
4. Хранить историю согласий.
5. Немедленно отключать узлы при отзыве согласия.
6. Уведомлять пользователей о том, какие узлы обрабатывают запросы, если это требуется политикой.
7. Обеспечить возможность удаления данных по запросу.

## 17. Критерии приемки

Система считается принятой, если выполняются следующие условия:

1. Пользовательские запросы не направляются на узлы без подтвержденного согласия.
2. Узлы, возвращающие `401` или `403`, немедленно исключаются и блокируются.
3. Отзыв согласия вступает в силу не более чем за 5 секунд.
4. Все пользовательские запросы требуют аутентификации.
5. Применяются лимиты частоты, объема и длительности запросов.
6. Потоковые ответы корректно проксируются и прерываются при отключении клиента.
7. Ошибки возвращаются в совместимом формате.
8. Журналы не содержат промпты, ответы и секреты по умолчанию.
9. Административный доступ защищен отдельно от пользовательского.
10. Внешние поисковые источники отключены по умолчанию и используются только при явной настройке.

## 18. Открытые вопросы и допущения

Поскольку исходные требования не содержали ответа по ряду параметров, приняты следующие безопасные значения по умолчанию:

1. **Использование произвольных открытых серверов без согласия:** запрещено.
2. **Режим Discovery:** только инвентаризация и кандидаты, без маршрутизации.
3. **Активное сканирование:** запрещено.
4. **Хранение промптов:** отключено.
5. **Балансировка:** `least_connections_with_latency`.
6. **Повторы для генерации:** запрещены после начала обработки.
7. **Административные операции управления моделями:** не доступны обычным пользователям.
8. **Узлы без TLS:** не рекомендуются и могут быть запрещены политикой.

Для уточнения реализации рекомендуется отдельно согласовать:

- целевую нагрузку;
- требования к юрисдикции обработки данных;
- необходимость поддержки OpenAI-совместимого API;
- политику биллинга или бюджетов;
- требования к высокой доступности;
- формат уведомления владельцев узлов;
- процедуру реакции на жалобы.

## 19. Итоговое положение

Проект **Free Ollama API Gateway** должен реализовываться как управляемый, этичный и юридически безопасный прокси-шлюз, который агрегирует только те узлы Ollama, владельцы которых явно подтвердили участие, согласились с политикой нагрузки и обработкой запросов. Интеграция с Censys, GreyNoise, ZoomEye, Natlas и Criminal IP может использоваться только как вспомогательный источник инвентаризации или исследования и не должна приводить к автоматическому использованию обнаруженных серверов.
